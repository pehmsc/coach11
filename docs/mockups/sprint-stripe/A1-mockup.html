3. Stripe Checkout (hosted, não desenhamos nós)

Não desenhamos a página de checkout — usamos a página hospedada da Stripe. Configurações que enviamos via API:

  • ✓mode: "subscription"
  • ✓line_items: [{ price: STRIPE_PRICE_ID_INDIVIDUAL, quantity: 1 }]
  • ✓subscription_data.trial_period_days: 7
  • ✓payment_method_collection: "always" (cartão exigido durante o trial)
  • ✓automatic_tax: { enabled: true } (Stripe Tax IVA 23%)
  • ✓tax_id_collection.enabled: true (B2B: pede NIF; particular pode ignorar)
  • ✓invoice_creation.enabled: true + envio automatico
  • ✓locale: "pt"
  • ✓success_url, cancel_url apontam para nós
  • ✓customer_email: user.email (pré-preenchido)

7. Modelo de dados (migration)

-- Migration: adiciona campos Stripe a clubs

alter table public.clubs
  add column stripe_customer_id text,
  add column stripe_subscription_id text,
  add column subscription_status text
    check (subscription_status is null or subscription_status in
      ('trialing', 'active', 'past_due', 'canceled',
       'incomplete', 'incomplete_expired', 'unpaid', 'paused')),
  add column subscription_current_period_end timestamptz,
  add column trial_ends_at timestamptz,
  add column subscription_cancel_at_period_end boolean not null default false;

create unique index clubs_stripe_customer_id_idx
  on public.clubs(stripe_customer_id) where stripe_customer_id is not null;
create unique index clubs_stripe_subscription_id_idx
  on public.clubs(stripe_subscription_id) where stripe_subscription_id is not null;

comment on column public.clubs.subscription_status is
  'Estado da subscricao Stripe. NULL = nunca subscreveu (clubes sales-led ou pre-Stripe).';

-- Tabela de eventos Stripe processados (idempotencia)
create table public.stripe_webhook_events (
  id text primary key,           -- Stripe event id (evt_...)
  type text not null,            -- ex: "customer.subscription.updated"
  processed_at timestamptz not null default now(),
  payload jsonb
);

Porque uma tabela de eventos?

Stripe pode reenviar o mesmo webhook em caso de timeout. Gravar o event.id evita re-processar — se já existe row, devolvemos 200 OK sem mexer no DB.

9. Decisões para fechar antes de codar A1

a) Onboarding-then-Stripe ou Stripe-then-onboarding?

Proposta: register → onboarding (cria clube) → Stripe Checkout. Permite ao treinador ver o produto antes de dar cartão; reduz friction. Trade-off: clube fica em DB sem subscription_status (NULL) até pagar. Tratamos como "trial não iniciado" — guard redirige para Checkout se tentar usar mais que 1 dia sem subscription. Concordas?

b) Acesso durante past_due

Mockup mostra "read-only após +3 dias". Alternativa: bloquear imediatamente (mais agressivo) ou nunca bloquear (Stripe trata sozinha mas perdes leverage). Recomendo read-only após 3 dias.

c) Re-checkout se incomplete

Se utilizador abandona o Checkout, fica com plan_type='individual' mas sem subscription. Ao próximo login, redirigimos para /precos? Ou mostramos botão "Completar subscrição"?

d) Email "trial a terminar"

Stripe envia automaticamente "trial ending soon" 7 dias antes do fim. Mas o nosso trial é só 7 dias → o aviso seria no dia 1. Posso desactivar o aviso Stripe e enviar manualmente no dia 5 via Resend, ou deixar a Stripe trear. Recomendo deixar Stripe (zero código).

e) Conversão clube → individual?

Se um clube sales-led quiser migrar para self-service individual, hoje não é suportado. Vamos ignorar (raro) ou bloquear explicitamente nas validações? Recomendo bloquear: tier='club' não pode usar /precos checkout.
