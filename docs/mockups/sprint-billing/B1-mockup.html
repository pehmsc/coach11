5. Modelo de dados

Migration unica criando tabela invoices

create table public.invoices (
  id              uuid primary key default gen_random_uuid(),
  club_id         uuid not null references public.clubs(id) on delete restrict,

  -- Identificacao
  invoice_number  text not null,        -- N.º do software fiscal (ex: FT-2026/007)
  period_start    date,                 -- Inicio do periodo de cobranca (opcional)
  period_end      date,                 -- Fim do periodo de cobranca (opcional)

  -- Datas
  issued_at       date not null,        -- Data de emissao
  due_date        date not null,        -- Vencimento

  -- Valores
  amount_cents    integer not null check (amount_cents >= 0),  -- valor em centimos
  currency        text not null default 'EUR' check (length(currency) = 3),

  -- Status
  status          text not null default 'issued'
                  check (status in ('issued', 'paid', 'cancelled')),
  paid_at         date,                 -- Data efectiva do pagamento

  -- Anexos / notas
  pdf_path        text,                 -- Path no Supabase Storage (bucket privado)
  notes           text,                 -- Notas internas (NAO visiveis ao cliente)

  -- Audit
  created_at      timestamptz not null default now(),
  created_by      uuid references auth.users(id),
  updated_at      timestamptz not null default now(),

  -- Constraints adicionais
  unique (club_id, invoice_number),
  check (period_end is null or period_start is null or period_end >= period_start),
  check (status != 'paid' or paid_at is not null)
);

create index invoices_club_id_idx on public.invoices (club_id);
create index invoices_status_due_idx on public.invoices (status, due_date);

-- View derivada: overdue = status='issued' AND due_date < today
-- (Calculado dinamicamente, nao precisa de coluna nem trigger)

alter table public.invoices enable row level security;

-- Super-admin (gate via get_super_user_access): tudo
create policy "invoices_admin_all" on public.invoices
  for all using (get_super_user_access());

-- Coordenador do clube: SELECT (read-only) das proprias facturas
create policy "invoices_club_coordinator_select" on public.invoices
  for select using (
    exists (
      select 1 from public.team_staff ts
      join public.teams t on t.id = ts.team_id
      where t.club_id = invoices.club_id
        and ts.user_id = auth.uid()
        and ts.role = 'coordinator'
    )
  );

-- Audit trigger (reusar padrao existente do schema)
create trigger invoices_updated_at before update on public.invoices
  for each row execute function set_updated_at();

Storage bucket

  • Bucket invoices, privado
  • Path: {club_id}/{invoice_id}.pdf
  • RLS no storage: super-admin escreve, coordenador do clube le apenas os seus

Helpers TypeScript

  • formatCents(amount_cents, currency) → "150,00 €"
  • isOverdue(invoice) → status='issued' && due_date < today
  • daysOverdue(invoice) → diferenca em dias

6. Decisoes pendentes (antes de codar B1)

a) Onde fica a entrada do coordenador?

Proposta: link "Facturacao" dentro do menu Configuracoes (com badge numerico se houver em aberto), e card na home se houver atraso. Alternativa: item dedicado no sidebar/bottom-nav.

b) Quem ve do lado do clube?

Proposta no mockup: so coordenador. Treinadores/staff nao veem. Faz sentido ou queres tambem para staff "admin financeiro" se um dia existir?

c) "Estornar" pagamento

No mockup admin existe um "estornar" para reverter status 'paid' → 'issued'. Util para erros de marcação, mas pode-se adiar para PR seguinte. Manter ou tirar?

d) Valor em centimos vs decimais

Proposta: centimos (integer) para evitar floating-point. Mostrado formatado na UI ("150,00 €"). Padrao Stripe. Concordas ou preferes numeric(10,2)?

e) Notificar quando uma factura e emitida?

Hoje proposta e nao enviar nada automaticamente (sales-led, Pedro envia por fora). Email automatico ao criar factura pode ficar para B3. Concordas?
